# dsh-daughter 0.8.2 更新说明

> 基线：0.8.1 · 日期：2026-11-21
> 优化：反馈提交逻辑，流程更短更直白。

## 更新公告与致歉

先说声抱歉。

0.8.0 的意见反馈在你本机提示「同步失败：fetch failed」，我没有先在同类环境复现就发了版；0.8.1 修好了 TLS，却又留下「重试同步」「复制内容」几个按钮，提交并不干脆。连着三次更新、反复重启 DSH，占用了你的时间，这是我这边的流程问题，不是你操作的问题。

问题的根因是 Windows 本机代理使用自己的证书链，Node 内置 `fetch` 不信任它，请求还没发出就失败；跟令牌、仓库权限都无关。0.8.2 把这条路径收成一句话：**填完，点一次「提交」**。能同步就同步并回显 Issue 编号；不能同步就留本地，下次打开自动补发，同时给你一个手动提交的链接。

以后涉及「用户要点击Submit」的功能，我会在发版前用真实 DSH 环境走一遍完整提交路径，而不是只靠单元测试和 curl 验证。再次抱歉，也谢谢你把截图发过来——那张截图直接定位了根因。

## 改动

### 提交逻辑

- 传输方式按平台一次选定：Windows 直接用系统 curl（使用 Windows 证书链），其他平台用 fetch；测试仍可注入 fetch。删掉「先 fetch、失败再 curl」的嵌套分支。
- 新提交与待发补发共用同一条 `sendOne` 路径：要么同步成功并记下 Issue 编号，要么留下预填 Issue 链接，没有第三种状态。
- 每条反馈只在结束时写一次队列记录，不再先写 pending 再反复改写；补发直接更新队列中的真实对象。

### 界面

- 反馈表单只保留一个「提交」按钮；删除「重试同步待发条目」和「复制内容」按钮。
- 打开反馈页时若发现待同步条目，自动补发一次，不再要求用户手动点击。
- 提交后的提示简化为两句话：成功显示 Issue 编号；未同步显示「已保存到本地，网络恢复后会自动补发」并附手动提交链接。
